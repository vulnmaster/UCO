# Revised Modular Structure for UCO Observable Ontology

## Overview of Existing UCO Observables
The Unified Cyber Ontology (UCO) Observable module currently contains a broad range of classes representing cyber artifacts (files, network packets, user accounts, etc.) and associated Facet classes that group their properties. In total there are hundreds of observable classes and facets in UCO (over 150 under the uco:observable namespace) spanning many domains​. For example, UCO defines classes like File, Process, IPAddress, DomainName, EmailMessage, UserAccount, etc., each with a corresponding Facet class capturing its attributes. This facet-based design (inherited from the CASE ontology) groups properties into re-usable bundles attached to objects​. While this provides flexibility and detail, the monolithic structure of the observables ontology can be overwhelming. There is a need to partition the ontology into disjoint modules aligned with distinct cyber domains to improve clarity and adoption.
Currently, many observable classes are direct subclasses of a generic ObservableObject without higher-level grouping, meaning concepts like files, network traffic, and accounts all live in one namespace. Some mid-level abstractions exist (e.g. Device with subclasses like DigitalCamera or GamingConsole​, or Account with subclasses like DigitalAccount​), but by and large the ontology isn't yet segmented by domain. The goal is to define clear modular groupings – each covering a disjoint area of cyber observables – such that no class overlaps between modules. Disjoint modules will help avoid confusion (an IP address won't also be classified as a file, for example) and make the ontology easier to extend for specific domains. Below we propose a revised breakdown of observable ontology modules, reviewing existing coverage and incorporating additional domains that practitioners recognize as distinct.

## Gaps and Additional Domains for Observables
Before defining the modules, it's important to identify which cyber domains are not fully covered by the current ontology. By reviewing industry frameworks and literature, we find a few notable gaps:
Cloud Infrastructure and Virtualization: UCO has extensive host and network artifacts but lacks explicit representation of cloud or virtual resources (no classes for virtual machines, containers, cloud services, etc.). Modern frameworks like MITRE ATT&CK treat Cloud and Container environments as distinct platforms, indicating the need for cloud-specific observables​. For example, ATT&CK defines data sources for Cloud Service activity​, and Elastic's common schema notes that hosts can be physical or virtual (including Docker containers and Kubernetes nodes)​. Introducing cloud/virtualization observables (e.g. VM instances, container images, cloud storage objects) will fill this gap.

Industrial Control Systems (ICS) and OT: The current ontology is focused on IT artifacts; it does not define observables unique to industrial control systems (e.g. PLC devices, SCADA tags, field sensor readings). MITRE has a dedicated ICS ATT&CK matrix​ and identifies ICS-specific data sources (like device asset inventories and control logs)​. Practitioners in critical infrastructure security would expect observables for control system components. A new ICS module can introduce classes for controllers, actuators, sensor telemetry, etc., kept disjoint from IT network observables.

Social Media and Online Content: UCO does include some classes for social media (e.g. Tweet, WikiArticle, ForumPost) and web artifacts (BrowserBookmark, Cookie, URLHistory), but these could be better consolidated into their own module. The ontology can be improved to cover online content observables such as social media profiles, posts, and metadata in a coherent way. This is a growing area in cyber investigations (for OSINT and digital forensics), and having a dedicated module would highlight its importance.

Multimedia (Video) Content: While there are classes for images (RasterPicture) and audio (Audio), there is surprisingly no class for video files or streams. Given the prevalence of video evidence (CCTV footage, screen recordings, body-cam video in investigations), adding a Video observable (with a facet for properties like encoding, duration, etc.) would improve completeness. This can be grouped with other content/media observables.

General Missing Artifacts: Other niche areas that could merit observables include application-specific logs (beyond the generic EventLog), configuration artifacts (the ontology has Windows Registry keys, but perhaps not things like cloud configuration or application config files), and DevOps/CI artifacts (build pipelines, code repositories). These are less universally recognized than the major gaps above, but worth noting for future extension. Overall, the most pressing additions are cloud and ICS domains, since these are explicitly recognized in industry frameworks as separate domains of activity​.

With these gaps identified, we can confidently propose a modular breakdown that not only covers all existing observables but also introduces new modules for the above domains. Each module is designed to be strictly disjoint from the others – an observable belongs to one module's hierarchy and not to any other – and aligns with how practitioners mentally categorize cyber observables.

## Proposed Observable Ontology Modules
Below is a revised breakdown of UCO observable modules, each corresponding to a distinct cyber domain or category of artifacts. We list the main classes each module would contain (including existing ones and any new additions), and provide justification for the module drawn from industry standards (MITRE ATT&CK, NIST, vendor schemas, academic sources) to ensure its relevance and disjointness. Each module would define a top-level abstract class (subclass of ObservableObject) to group its observables, and these top classes would be defined as mutually disjoint to enforce separation.

### Core Observables Module
Purpose: Define the base classes (e.g., Observable) and common properties shared across domains. This module serves as the foundation that each domain module can extend—but the domain-specific classes themselves will be kept disjoint.

Key Components:

Observable: The root class.

Common Properties: Timestamp, source, context, etc.

Note: Although this core module is shared, its classes are not directly instantiated for domain-specific artifacts; rather, they are extended by the domain modules.

### Network Observables Module
Contents: Artifacts related to networks and communications infrastructure. This module includes classes such as IPAddress (and IPv4Address/IPv6Address), MACAddress, DomainName, URL, AutonomousSystem (AS), network connection/flow objects (NetworkConnection, NetworkFlow, Socket, WirelessNetworkConnection), and DNS artifacts (DNSRecord, DNSCache). It would also cover any network configuration or protocol objects (NetworkInterface, NetworkRoute, etc.). All these represent network-layer observables.

Justification: Network telemetry is a foundational category in cybersecurity. MITRE ATT&CK's data source taxonomy explicitly lists network-based observables – e.g. network traffic, DNS, and IP addressing – as key data for detection​. In STIX 2.1, network traffic and related objects (IP addresses, domains, URLs) are core observable types​. Security operations and SIEM schemas (like Elastic ECS) separate network data from host data, underscoring this as a distinct area​. By having a Network module, all network observables (addresses, protocols, connections) are kept together and disjoint from, say, host or file observables. This ensures, for example, that an IPAddress individual cannot also be mistaken for a file or device – a clean separation aligned with networking as its own domain. Practitioners can choose to import the Network module when they need to represent indicators like IPs, domains, or PCAP data, without pulling in unrelated concepts.

### Host & System Observables Module
Contents: Artifacts found on endpoints or operating systems. This module groups file system objects and OS/runtime objects. It includes classes like File (and specialized file types such as ArchiveFile, PDFFile, etc.), Directory, file system metadata (Filesystem, MFTRecordFacet, NTFSFile and other file system facets), and memory and process artifacts (Process, Thread, Memory, Mutex, Semaphore, etc.), as well as operating system structures (OperatingSystem and OS-specific classes like WindowsRegistryKey, WindowsEvent, WindowsService, UnixProcess, etc.). Essentially, any observable that is part of a computer's host system – files, executables, processes, OS configs – falls here. Hardware devices attached to a host (disk drives, partitions, USB devices) can also be included or could form a sub-module if needed (see Device module below).

Justification: In practice, "host-based" evidence is treated as a domain distinct from network data. Incident responders talk about host artifacts (files, processes, registry) separately from network indicators. Elastic's taxonomy defines a Host field set for attributes of a computing instance (covering OS, hardware, etc.), and MITRE maps many techniques to host observables like file creation, process execution, or registry modification​. By consolidating these in one module, UCO aligns with the common notion of endpoint telemetry. This module would be one of the largest (given UCO's detailed file and OS coverage), but it can be internally sub-divided (e.g. file sub-hierarchy vs. process sub-hierarchy) while remaining one logical unit. All classes here share a context – they reside on a computing device. Marking Host observables disjoint from Network observables is intuitive (an IP address or domain is not a host artifact, and a file or memory segment is not a network entity). This disjointness reflects real-world data source separation (host logs vs. network logs)​. For adoption, a security engineer interested in host forensics (Windows registry, file analysis, memory forensics) can import just this module and get all relevant classes without the noise of unrelated concepts.

### Identity & Account Observables Module
Contents: Digital identity information and account credentials observed in systems. This module covers classes such as UserAccount (and OS-specific accounts like WindowsAccount, UNIXAccount), online or application accounts (DigitalAccount, EmailAccount, PhoneAccount, etc.), and associated credentials or profiles (Credential, Password – if represented, or CredentialDump). It also includes contact and address observables that are part of user/account data: Contact entries, EmailAddress, PhoneNumber (phone account), SIPAddress, and so on. Essentially, any observable that represents a user account or identity artifact (apart from the human identity itself, which is handled in the separate Identity ontology) belongs here. This module bridges between pure cyber artifacts and the people/organizations using them.

Justification: Both threat intel and incident investigations often categorize accounts separately, because they tie to user identities and access management. MITRE's data source list has "User Account" and related events (creation, authentication, modification) as a distinct category​– this indicates accounts are a well-understood area of observables. UCO already models accounts in detail (with facets for authentication, account properties, etc.), so modularizing them makes that portion more accessible. We ensure disjointness by confining account objects to this module – for example, an account cannot be mis-classified as a file or a network object. This is logical since an account is an abstract digital identity, not a tangible host artifact or network element. Keeping account observables separate also aligns with access management domains (for instance, an IAM specialist can focus on this module). As an improvement for practical use, clearly distinguishing account observables helps in integrating with identity management systems and compliance frameworks that track user accounts.

### Software & Execution Observables Module
Contents: All classes related to software, applications, and code execution on systems. This includes the generic Software class and its intended specializations (which could be expanded per ongoing UCO development​): for example, Application (end-user software), Library (software library), OperatingSystem (also listed under host, but conceptually an OS is software), ExecutableCode or script (if added), and possibly new classes like SoftwarePackage or ContainerImage as specialized software distributions. This module also encompasses software configuration items: e.g. ConfigurationFile or ServicePack (patch) if those become classes. Note that Process is an executing instance of software, which we kept in Host module; here we focus on the static software entities themselves (installable or installed software). We might also include Malware as a concept (though UCO thus far uses the same Software class for malware, adding a MaliciousTool role externally). If needed, subclasses for scripts or packages would be defined here as new additions to cover code artifacts not currently distinguished.

Justification: Differentiating software as its own module is supported by the way practitioners think about software inventory and malicious code. For instance, NIST guidance emphasizes ability to characterize different types of software objects (software, application, script, library, package, OS, etc.) for forensic analysis. The UCO project itself has identified the need to restructure the software hierarchy to add concepts like Script and Package​ . By isolating software observables, tools that focus on software metadata (e.g. inventory tools, malware repositories) can just use this module. It stays disjoint from host/hardware – a Software object is not a physical device or file, but an abstract representation of code. (The file that contains a software binary would be a File in Host module, but the software product is a separate notion – this separation resolves the debate where, for example, a software package file could be both a file and a software​. In our modular approach, the file aspect is in Host, and the software aspect is in Software module, linked via relationships if needed). Industry frameworks also treat software as distinct; for example, ATT&CK has specific technique data around software and application logs​. Ensuring this module's disjointness (no overlap with Account or Network, etc.) is straightforward – a piece of software isn't simultaneously an account or an IP address. This clarity can improve adoption by making the ontology easier to navigate (users immediately see where to represent an application vs. a running process vs. a user account).

### Communication & Messaging Observables Module
Contents: Observables that involve communication content between parties, apart from network-level metadata. This includes electronic messages and communications such as EmailMessage (and components like EmailHeader if modeled), SMSMessage, MMSMessage (if added), InstantMessage or chat (could be represented via a generic Message class), PhoneCall records, and possibly VoIP call logs or VoiceMail (if needed). It also contains related things like MessageThread or conversation groupings, and attachments or content within messages (Attachment facets, etc.). Essentially, this module covers the content layer of communications – what was said or sent, as opposed to the network transport.

Justification: Email and messaging are often treated as a distinct data source in cybersecurity. Many security products specialize in email security or SMS/phishing message analysis, indicating this is a recognizable category. While network transports carry these communications, practitioners will refer to "email artifacts" separately from raw network packets. UCO already has rich classes for emails, including EmailAccount and EmailAddress (which are in the Account module) and EmailMessage with facets for headers, bodies, etc. Grouping them in a Communication module highlights their identity. This is backed by frameworks like ATT&CK, which associates certain techniques with email or messaging (for example, phishing involves email observables). NIST's evidence types also indirectly support this – they mention electronic messages and online accounts as evidence separate from files​. In our modular breakdown, Communication observables are disjoint from Network observables (an email message vs. an IP address) and from File/Host (an email is not a file on disk, though it may be stored as one – the abstraction is different). This disjointness again reflects real usage: analyzing an email's headers and content is a different context than analyzing a filesystem artifact. By having a dedicated module, organizations focused on messaging (e.g. investigating an email-based attack) can use the ontology without pulling in unrelated host/network classes. It improves usability and ensures the ontology speaks the language of email/messaging analysts.

### Social Media & Online Content Observables Module
Contents: This module contains observables that originate from social media platforms, forums, wikis, and general web content that is user-generated. Classes include SocialMediaProfile or the existing Profile/OnlineAccount concepts for a user's account on a platform, Tweet (with a TwitterProfileFacet already in UCO for Twitter-specific profile info), Post (could be a generic for forum or social media post), ForumPost, ForumMessage, WikiArticle, and web browsing artifacts like BrowserBookmark, BrowserCookie, URLHistory and URLVisit. It may also cover e-commerce or dark web content like the ShopListing class present in UCO. Essentially, any artifact that is content on the internet (outside of private communications) and often publicly viewable falls here.

Justification: The rise of social media in investigations (both for crime and threat research) means practitioners see these observables as a distinct category. Academic works on cyber investigations note the need to handle social media data alongside traditional logs​ (CASE, for instance, expanded to cover more domain concepts in its MVP​, which included online activities). From an ATT&CK perspective, social media might not be a "data source" for enterprise defense, but it is critical in threat intelligence and OSINT. Vendors and law enforcement have taxonomy branches for "Web & Social Media" when organizing indicators. Thus, a Social Media module in the ontology aids adoption by those use-cases. It remains disjoint from Communication (though there is some overlap, e.g. direct messages on social platforms could be considered Communication; we can decide whether those belong here or in the comms module). It's also disjoint from Accounts (a social media account would be represented via an account object linked to a Profile observable, rather than conflating the two). Keeping these observables separate ensures clarity – e.g., a Tweet is not confused with an EmailMessage, and a BrowserCookie is not treated as a file or an IP address. This module can improve practical use by providing a one-stop schema for any artifacts gathered from open web sources, facilitating integration with OSINT tools and dark web monitoring platforms.

### Device & Hardware Observables Module
Contents: Physical or virtual devices and hardware components that are observed in a cyber context. This includes classes like Device (general equipment), and its subclasses: for example, Disk and DiskPartition (storage media), Volume (logical storage), Memory (physical memory object), peripheral device artifacts (Adaptor, DigitalCamera, GamingConsole as already in UCO​), network appliances (NetworkAppliance, SecurityAppliance), and mobile devices (MobileDevice, SIMCard). It could also cover virtual devices in the host, like VirtualMachine or Container (as new classes to represent those environments). Note that some of these currently appear under other groupings (e.g. SIM card under Mobile, disk under file system). In the new modular view, we gather them as "Device" observables since they represent distinct pieces of equipment or storage media, separate from the data they hold.

Justification: Practitioners often differentiate hardware or device evidence from data evidence. For example, NIST defines "physical media" as a type of digital evidence separate from the files and accounts on it​. Having a module for Device observables lets investigators describe the device itself (e.g. a seized hard drive, a USB stick, a mobile phone) as an object with properties (manufacturer, serial number, etc.). UCO already provides facets for device attributes like model, serial, and even manufacturer (linking to an Identity). By isolating these in a Device module, we ensure disjointness from, say, File or Network modules – a Disk or MobileDevice is not a file or a network flow; it's a higher-level entity. This is aligned with how cases are handled: one first identifies the devices involved, then the data on them. Industry schemas like ATT&CK's "Asset" data source for ICS​ also show the concept of devices as distinct items to inventory (though in ATT&CK's case, ICS assets). Additionally, Elastic's ECS treats the host as an entity with hardware attributes and allows identifying distinct host machines by an ID,​ which is analogous to treating a device as an observable object. The Device module would improve ontology adoption by cleanly supporting use cases like hardware inventory management, incident triage (listing affected devices), or chain-of-custody tracking for forensic media – all without conflating device objects with the data contained on them.

### Cloud & Virtual Infrastructure Observables Module (New)
Contents: New classes and concepts representing cloud computing and virtualization artifacts. This module would introduce objects such as CloudInstance (a virtual machine instance in a cloud or virtual environment), Container (e.g. Docker container artifact), and CloudService (a generic class for cloud-provided services or resources). It could also include cloud-specific account analogs (like a CloudAccount or CloudCredential for things like AWS access keys, though those might be handled under Account module) and cloud storage observables (CloudStorageObject for things in S3 buckets, for instance). Another inclusion could be virtualization host artifacts (a Hypervisor or VirtualNetwork if needed). The key is that these are observables not tied to a physical host – they exist in virtualized or cloud environments.

Justification: The need for a Cloud module is strongly supported by the evolution of attack frameworks and industry focus. MITRE ATT&CK Enterprise covers SaaS and IaaS platforms, and lists "Cloud Service" as a data source category​, indicating that defenders consider cloud logs and resources separately from on-premise host logs. Moreover, the ATT&CK matrix explicitly includes techniques targeting containers and cloud infrastructure (e.g. container escape, cloud credential misuse), which implies observables in those areas. Elastic's definition of host types includes virtual machines and containers as hosts​
– reinforcing that these are first-class entities to be modeled. Currently, UCO has no explicit classes for these, so adding them improves the ontology's relevance. By keeping this module disjoint, we say a CloudInstance is not the same as a physical Device or a Host in the traditional sense (though it can have relationships to those, like a virtual host runs on a physical host). This separation mirrors real deployments: an investigator might separately list compromised cloud VMs versus on-site servers. A cloud module also aids adoption in cloud-heavy environments – for example, a DFIR analyst working a cloud incident can directly represent cloud VM artifacts and API logs using this ontology. Strict disjointness from other modules ensures we don't confuse, say, a CloudStorageObject with a generic File (they have different properties and context). Overall, this addition modernizes UCO to cover "cloud-first" scenarios, which is increasingly important for practical use​.

### Industrial Control Systems (ICS) Observables Module (New)
Contents: New classes representing industrial and operational technology systems. This module could include observables like ICSDevice (abstract parent for ICS components), PLC (Programmable Logic Controller), RTU (Remote Terminal Unit), HMI (Human-Machine Interface) and other common control system devices. It would also cover ICS-specific network/protocol artifacts (e.g. FieldbusPacket or SCADAFrame if modeling low-level protocol messages) and process control data points (ControlLoop, SensorReading, etc., if needed to capture telemetry). Additionally, one might have classes for physical process indicators (temperature, pressure readings as digital observables) as reported by sensors. These go beyond traditional IT observables into the cyber-physical realm.

Justification: Critical infrastructure security has unique needs, and ATT&CK for ICS exists precisely because the tactics/techniques and data sources differ from enterprise IT​. MITRE's ICS matrix highlights devices like PLCs and engineering workstations, and their data sources include things like "Device asset inventory" and control network traffic​. Presently, UCO doesn't cater to this domain, which could hinder adoption in ICS contexts. By introducing an ICS module, we allow representation of those elements in a way that's separate from normal IT observables. For example, an PLC object can have facets for firmware version, program logic, etc., without overlapping with, say, the Software module (the PLC is an embedded device, not just software). Disjointness is clear here – an ICS device is not an ordinary computer or user account or network observable (even though it communicates via networks, we'd model its network traffic via existing network classes linked to it). Ensuring the ICS module stands apart prevents confusion (e.g., not treating a PLC as a generic "Device" from the Device module, since it has specialized attributes and significance). This specialization improves practical utility: cybersecurity practitioners in industrial sectors can adopt UCO knowing it has a place for their domain-specific observables, which eases integration of OT (operational technology) data with IT data for holistic situational awareness​. It also aligns with NIST's push for integrating cyber-physical systems security – acknowledging "other digital objects" like online control systems as evidence​. Overall, the ICS module is a new addition that significantly broadens UCO's coverage while maintaining a clean separation from existing modules. (Depending on scope, additional modules could be defined. For instance, one might separate a "Malware Analysis" module for dynamic analysis artifacts, or a "Logs & Events" module to capture event records in a generalized way. However, the nine modules above cover the major domains requested and keep the ontology modular.)

## Ensuring Disjointness and Integrating Frameworks
In the revised design, each module corresponds to a set of classes that are mutually exclusive with those of other modules. This can be enforced by introducing high-level classes (e.g. NetworkObservable, HostObservable, etc.) that partition the ObservableObject space and declaring them owl:disjointWith each other. For example, all network-related classes would subclass NetworkObservable, all file and process classes subclass HostObservable, etc., and those top classes do not overlap. This strict disjointness was a key goal to support modularization and follows ontology best practices to avoid ambiguity in class membership​. It also reflects the "simple, mutually exclusive categories" approach recommended in taxonomies for incident information sharing​. By structuring the ontology this way, a user can mix-and-match modules (importing multiple as needed) confident that the same real-world entity won't be modeled in two inconsistent ways. If something legitimately spans domains (e.g. a piece of malware might involve a file observable and a software observable), the ontology would handle it via relationships between module classes rather than a single class in multiple modules.

Another important improvement for adoption is alignment with industry terminology and frameworks. We justified new modules with references to MITRE ATT&CK data source categories, NIST guidelines, STIX 2.1 observables, and vendor schemas (like Elastic ECS and OCSF). This means the ontology's structure will feel familiar to practitioners. For instance, having a Network module that cleanly maps to "network indicators" or a Cloud module that maps to "cloud telemetry" helps users mentally connect UCO concepts to their own data. OCSF's taxonomy explicitly calls out observables like IPs, domains, file hashes, URLs as fundamental pieces of threat info​ – UCO's modules cover all those and more, and now in an organized way. We also looked at the list of STIX Cyber Observable (SCO) types, and our modules encompass each (files, IPs, domains, mutexes, processes, user accounts, etc. each fall into one of the modules) ensuring no loss of compatibility with threat intel standards. Cross-referencing these frameworks provided validation that our module set is comprehensive: for example, every ATT&CK data source (Windows Registry -> Host module, Active Directory account -> Account module, Packet capture -> Network module, Cloud logs -> Cloud module, Control device logs -> ICS module, etc.) maps to one of the modules​.

## Improvements for Practical Use and Adoption
Finally, beyond just modularization, we highlight a few areas where the observable ontology can be improved for better adoption and usability:

Expanded Domain Coverage: The addition of Cloud and ICS modules (and possibly others like Video/Multimedia) addresses previously uncovered domains, aligning with the direction of CASE 1.0 which emphasized expanded coverage for MVP usefulness​. By covering more domains, UCO becomes a one-stop ontology for cybersecurity, reducing the need for ad-hoc extensions. This encourages adoption as organizations see their specific needs (cloud, IoT, ICS) are met out-of-the-box.

Clear Organization and Documentation: Breaking the ontology into logical modules with clear naming (Network, Host, Account, etc.) makes it more approachable. Each module can have its own documentation section explaining the scope and providing examples (e.g. showing how to represent a particular artifact type). This modular documentation is easier to digest than a single huge list of classes. It also facilitates training new users – they can focus on the module relevant to their job role (a network analyst reads about the Network module, a forensic analyst focuses on Host/Device modules, etc.).

Strict Disjointness and Consistency: As mentioned, enforcing disjoint classes eliminates confusion. It ensures data quality – for example, a File observable will never accidentally have properties that only apply to a UserAccount. This also helps tooling (SHACL shapes could be developed per module to validate that instances conform to the expected structure of that module's classes). The NORIA-O project noted the value of using OWL to add logical structuring like class disjointness for quality control​. UCO can follow suit by formally declaring disjoint modules and possibly cardinality constraints to strengthen consistency.

Integration with Other Standards: To improve adoption, UCO should make it easy to map to other common data schemas. For example, providing a mapping of UCO Network module classes to fields in Elastic Common Schema or Syslog, mapping Host module classes to MITRE's CAR (Cyber Analytics Repository) data model, etc. This crosswalk in documentation or as an appendix ontology (perhaps via owl:equivalentClass or vocab mapping) would demonstrate UCO's practical interoperability. Since many organizations already log events in formats aligned with those schemas, seeing how UCO observables correspond will increase confidence in using UCO. Our proposed modules were chosen to align with these external categorizations (network vs host vs identity, etc.), which will simplify such mappings.

Refinement of Complex Hierarchies: In some places, the observable ontology has very granular classes (especially OS-specific ones like dozens of Windows-specific artifacts). While detail is good, for practical use it might be wise to simplify or consolidate where possible. For example, consider if all those Windows registry artifacts need separate classes or if they could be facets of a generic RegistryKey. The modular approach allows this discussion in context – e.g., within the Host module, perhaps streamline the Windows sub-hierarchy. Likewise, the Software module can clarify the hierarchy of Software vs Application vs OS as the UCO issue discussion suggests. By addressing such design questions (possibly deprecating or merging some classes), the ontology becomes leaner and more intuitive. This process should be driven by practitioner feedback: which classes are actually used and which complicate matters without adding value.

Examples and Use Cases: To drive adoption, each module should come with example instances demonstrating real-world usage. For instance, an example of representing a phishing email (using Communication and Network modules together), or an example of an ICS incident (using ICS and Network modules). This can be provided in documentation or as sample TTL files. Practical, scenario-based examples help users see the ontology's value and lower the barrier to entry. It complements the formal ontology with guidance on how to apply it in investigations and threat intel sharing.

In summary, the UCO observable ontology can significantly benefit from a modular, domain-driven structure. The revised breakdown above provides distinct, disjoint modules covering all current observables and newly identified domains (cloud, ICS, etc.). This approach is grounded in industry best practices – as seen by parallels in ATT&CK's data source taxonomy and other schemas – and will make UCO more approachable to practitioners. By maintaining strict separation between modules and aligning with familiar categories, UCO's observables become easier to understand, extend, and integrate. These changes, along with simplifying class hierarchies and providing clear documentation, will improve UCO's adoption and practical utility in representing the myriad cyber observables that modern security operations and investigations encounter.
